# AI 替你敲回车之前：一个 SSH 客户端该把权力交给谁

## 一、问题不是「AI 会不会」，而是「谁点头」

把大模型接到终端，技术上没什么门槛：模型吐出一条命令，程序把它 paste 进 shell，回车一敲就执行。演示视频里很顺，真拿到生产机器上用，第一个绕不开的问题就是——**这条命令到底是谁让它跑的？**

我见过几种做法：

- 模型输出什么就执行什么，全程无人值守；
- 执行前弹一个确认框，但用户看都没看就点了同意；
- 做了「只读模式」，结果只是前端把按钮置灰，后端照样收写命令。

这几种都不能叫「安全」。AI-SSH-Pro 的思路是：**把策略做成显式的、可解释的、并且在最底层再校验一次的约束**，而不是靠用户记得点确认。

---

## 二、三档策略：让「AI 能做什么」变成一句能读懂的话

用户不需要理解 prompt engineering，也不需要记一堆开关。产品里只暴露三档，名字直接说明后果：

| 策略 | 实际行为 |
|---|---|
| **仅建议** | AI 只输出命令和建议，不碰终端 |
| **执行前确认**（默认） | 变更类命令需要你明确点确认才写入终端；只读类命令照常 |
| **自动执行** | 按策略直接执行；高风险动作仍可单独要求二次确认 |

三档同时可以全局设、按主机设、在单个标签页临时改。界面上始终显示**当前实际生效**的那一档，以及它是被哪里覆盖的——是全局默认、这台主机的设置，还是本标签页的临时选择。

这点比「设了就生效」更重要：当策略可以被多层覆盖时，用户最需要知道的是**此刻到底哪一档在起作用**。所以界面里专门显示来源，比如「临时 / 此主机 / 全局」，而不是让人去翻三层设置。

## 三、把「主机类型」纳入权限模型

只靠执行策略还不够，因为同样的命令在不同机器上风险完全不同。所以每台主机还有一个**保护级别**：

- **普通**：按你选的策略走。
- **生产**：保留你选的策略，但标签页顶部常驻提醒，避免看错机器；绝不因为「这是生产机」就偷偷降权让你莫名其妙。
- **只读**：AI 对这台机器的写入被**主进程**直接拒绝——注意，是在主进程里拦，不是在渲染层的界面上把按钮变灰。哪怕界面上点了「同意」，写命令也过不去。

这是我觉得整个设计里最关键的一条：**权限校验不能只做在 UI 层**。UI 层的限制是给用户看的提示，主进程才是最后一道闸。两处都做，才不会出现「界面显示不能写，但消息已经发出去了」这类问题。

## 四、敏感字段不进 AI，也不进对话

另一条边界是凭据。密码、私钥口令、API Key 这几类字段：

- 由用户在本地填写，AI 不会代填；
- 不会作为上下文发给模型；
- 会话密码和 API Key 使用操作系统安全存储（如 Windows DPAPI）加密，不随项目文件分发。

这条规则的实现细节比口号重要：不是「提示模型不要问密码」，而是在数据流的源头上就不把这些字段送进 AI 上下文。即使模型自己输出了看起来像密钥的内容，也不会被自动填进任何输入框。

## 五、做完要能查：审计不是摆设

任何由 AI 触发的动作，都会记进审计日志：时间、哪台主机、什么动作、执行结果。可以按类型筛、按结果筛。

审计的意义不是事后甩锅，而是让「AI 做了什么」变成可核对的事实。一个不记日志的 AI 助手，出问题时你连复盘都做不了。

## 六、为什么默认不是「自动执行」

这个问题被问得最多。答案不是「自动执行不好」，而是**默认值要匹配大多数人的真实心态**：装一个 SSH 工具，第一反应是「先看看它靠不靠谱」，而不是「立刻让它接管我的服务器」。

所以默认给了「执行前确认」：AI 给方案，你过一眼再放行。用熟了，再按主机或按场景切到自动执行——这是一个**逐步授权**的过程，而不是一上来就要求用户信任。

---

## 七、写在最后

AI 进入运维场景，最容易被忽略的不是能力上限，而是**授权边界**。一个会观察终端、会规划步骤的助手当然好用，但只有当它能清楚地回答「刚才那条命令是谁让跑的、在哪台机器上跑的、依据什么策略跑的」时，才配得上生产环境。

AI-SSH-Pro 是我的回答：观察 → 计划 → 确认后再执行，主机保护落到主进程，敏感字段不进 AI，动作必留审计。
